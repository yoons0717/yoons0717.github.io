# 블로그 글쓰기 가이드

Incident Radar 개발기 시리즈 규칙. 새 글 쓰기 전, 리뷰 전에 훑을 것.

## 0. 대전제 — 개발된 버전 기준으로 쓴다

각 편은 **그 시점에 실제로 커밋된 코드**만 다룬다. 계획서·설계 노트·`BLOG_DRAFT.md`·코드 doc 주석의 "의도 / 최종 사용법"을 현재 구현인 것처럼 옮기지 않는다.

- 스니펫은 실제 파일에서 그대로. `grep`으로 **그 코드를 호출/테스트하는 곳이 지금 있는지** 확인.
- 등록만 되고 소비자 없음(예: `Clock` 프로바이더) → 안 다루거나 "이후 편에서 씀"으로 분리.
- 테스트 개수·크기·시간 등 숫자는 실제 실행 결과에서. 기억으로 쓰지 않는다.
- 아직 안 만든 목표 동작은 개요(0편)에서만, 본문이면 "예정"으로.
- **시점 스코프 vs 거짓**: "2편 시점엔 `/health`뿐"(그 태스크 기준 참 → OK) vs "프론트가 `shared`를 import"(코드엔 없음 — 이런 건 잡아낼 것).

## 1. 파일 · frontmatter

- 파일명 `incident-radar-N-topic.md` (kebab, `N`은 `seriesOrder`와 일치)
- 이미지 `src/content/blog/images/N-용도.png`

```yaml
---
title: "[Incident Radar N] 이번 편 한 줄 제목"
description: 한 문장. 무엇을 만들었는지 구체적으로.
pubDate: 2026-09-01
tags: [개발]
seriesOrder: N
---
```

키 사이 빈 줄 금지(에디터가 넣으면 지운다). `seriesOrder` 있어야 이전/다음·정렬에 들어감.

## 2. 구조

```
인트로 (2~4문장)
## 주제 1 / ## 주제 2 / ### 하위 파트 …
## 검증        (이번 태스크 확인 방법 — 없으면 실습 워크스루로 대체)
```

- `##` = 주요 주제이자 **자동 목차 항목**. 목차에 나와도 되게 이름 명확히
  ("개발 흐름" X → "스키마 변경 흐름" / "실행 흐름" X → "테스트를 한 번에 실행하기").
- 인트로: 앞 편이 준비한 것 + 이번 편이 만드는 것 + 범위 한 줄("이후 편에서 X"). 기계적 흐름 다이어그램 X.
- 겪은 함정 섹션은 기본적으로 만들지 않는다. 정말 필요한 시행착오만 해당 주제 문단 안에 "이렇게 하는 이유" 형태로 녹인다. "물린 얘기" 프레이밍·일반 상식("린트 ≠ 포맷") X.
- 검증: 실제 명령·테스트·출력. 추상 체크리스트 X.
- "## 다음 편" 티저 섹션 만들지 않는다.

### 흐름 — 독자가 조각을 순서대로 받게 한다

- **인트로에 지도 한 줄.** 세부에 들어가기 전에, 이번 편의 계층·단계가 어떻게 이어지는지 한 문장으로("컴포넌트가 훅을 부르면 팩토리 → 엔드포인트 → `apiGet` 을 거쳐 검증된 값이 돌아온다"). 인트로의 이 한 줄만 예외고, 본문에서 같은 흐름을 다이어그램으로 다시 그리지 않는다.
- **`##` 하나에 한 가지 일.** 한 섹션에 주제가 둘이면 쪼갠다. 글의 등뼈(핵심 계층·파이프라인)는 최상위 `##` 로 두고 `###` 에 파묻지 않는다.
- **파이프라인을 다루면 섹션 순서도 그 순서를 따른다** — 안→밖이든 밖→안이든 한 방향으로.
- **개념은 처음 나오는 자리에서 설명하고, 뒤에서 처음부터 다시 꺼내지 않는다.** (간결성의 "중복"과 다름 — 이건 설명 *위치* 문제.)
- 한 `##` 밑 `###` 가 셋 이상으로 불어 비대해지면, 일부를 문단으로 흡수하거나 별도 `##` 로 올린다.

## 3. 말투

담백한 존댓말(`~합니다`) 하나로. 본문·워크스루·리스트 전부. 반말과 섞지 않는다.

| 쓰지 말 것 | 대신 |
|---|---|
| 그냥 귀찮습니다 / 번거롭습니다만 남발 | 불필요한 오버헤드입니다 |
| 띄우다 | 실행하다 / 올리다 |
| (프로세스가) 돈다 | 실행된다 |
| 번들에 박히다 | 번들에 포함된다 |
| SQL을 써 준다 | SQL을 생성한다 |
| 인덱스가 안 듣는다 | 인덱스가 제대로 활용되지 않는다 |
| 어차피 / 뒤엣것 / 내 저장소 | (빼거나) 프로젝트 저장소 |
| ~를 몰라도 됩니다 / 신경 안 써도 됩니다 (추상화 설명) | 그 계층이 하는 일을 그대로 |

AI스러운 티 제거:

- 문장 중간 볼드 남발 X — 정의하는 용어 첫 등장에만. 식별자는 `백틱`.
- `—`를 호흡용으로 X — 리스트 "용어 — 설명"에만.
- "핵심은 ~입니다 / ~는 뜻입니다" 구조 안내 상투구, "선택지는 둘입니다 → 대조 → 저는 X" 스캐폴드, 의인화, 섹션마다 요약 클로징 — 전부 X.
- 어려운 개념은 비유보다 구체. 추상 제목("계약을 코드로") X → 하는 일 그대로("요청·응답 형태를 한 파일에 정의한다").
- 이력서 링크될 수 있음 — "프론트 4년차 → 풀스택 전향 / 학습 프로젝트 / 초보" 자기비하·경력서사 X.

## 4. 간결성

- 같은 요점은 한 번만. 재진술·볼드 재강조·요약 클로징으로 부풀리지 않는다.
- 코드블록 바로 위 전이문("서비스에서는 ~합니다") 최소화 — 코드가 말하면 문장 뺀다.
- 텍스트 한 줄로 되면 다이어그램 만들지 않는다. **같은 흐름을 여러 섹션에서 반복해 그리지 않는다** (한 번, 제 자리에만).
- 큰 아키텍처 그림은 mermaid로 그린 뒤 SVG로 뽑아 `images/` 에 넣는다
  (`npx @mermaid-js/mermaid-cli -i x.mmd -o images/N-arch.svg -b white -t neutral`).
  작은 흐름은 텍스트 블록.
- 코드블록: 실제 파일 그대로, **줄 사이 빈 줄 넣지 않는다**. 펜스에 `id="..."` 붙으면 제거.

## 5. 이미지

- `src/content/blog/images/N-용도.png`, 본문에서 `![한국어 alt](./images/N-용도.png)`.
- alt는 화면 내용 설명("POST /errors 의 201 응답, body에 id·createdAt").
- 동작을 보여주는 스크린샷만. 잘못된 상태(500 등)는 "이럴 때 이렇게 보인다"로 조건 명시할 때만.
- 캡처 전엔 `<!-- 스크린샷 자리: ... -->` 주석. **없는 이미지 참조하면 빌드 깨짐.**

## 6. 자동으로 붙는 것 (신경 안 써도 됨)

- 이전/다음 링크: `seriesOrder` 기준, `BlogPost.astro` 하단.
- 상단 목차: `##` 3개 이상이면 자동.
- 목록 정렬: 같은 `pubDate`면 `seriesOrder` 역순(최신 위).
- 본문 이미지 클릭 → 전체화면 확대 (오버레이/`Esc`로 닫기).

## 7. 작업 순서 · 리뷰

1. **초안** — 실제 레포(`~/Desktop/myProject/Incident-Radar`) 해당 태스크 코드로.
2. **정확성 리뷰** → 3. **흐름 리뷰** → 4. **말투 리뷰** → 5. **구조·간결성 리뷰** (한 패스에 하나씩, 섞지 않는다)
6. **이미지** 캡처 → `images/`, alt.
7. **커밋** — 작업별로 나눠서(신규 글 / 기존 글 수정 / 템플릿 변경). 메시지 끝에 `Co-Authored-By` / `Claude-Session`.

흐름은 정확성 바로 다음. 순서·섹션 경계를 먼저 잡아야 그 뒤 말투·간결성 손질이 버려지지 않는다.

리뷰 원칙:

- 이상한 곳을 **먼저 보고**하고 사용자가 고르게 한다. 리뷰하며 바로 고치지 않는다(사소한 오타 제외).
- 재구성·삭제·병합·순서 변경은 제안하고 **컨펌 받은 뒤** 실행. "순서만 봐줘" → 문장 안 건드림.
- 고친 뒤 **다시 리뷰** (특히 정확성 — 고치며 새로 어긋날 수 있음).

패스별 체크:

- **정확성**: 코드 주석·설계 노트 근거로 쓰지 않기. 스니펫 = 실제 파일 + `grep`으로 소비자 확인. 현재형 문장의 주어가 지금 코드에서 실제로 그 동작을 하나. 예제 SQL·명령이 실존 형태인가.
- **흐름**: 인트로에 큰 그림 한 줄이 있나. `##` 마다 한 가지 일만 하나. 등뼈가 `###` 에 묻혀 있지 않나. 앞에서 설명한 개념을 뒤에서 처음부터 다시 꺼내지 않나. 섹션 순서가 다루는 파이프라인 순서와 맞나. `###` 가 셋 이상 달린 비대한 `##` 는 없나.
- **간결성**: 한 요점이 몇 번 나오나 센다. 중복 다이어그램. 코드 위 전이문.
- **말투**: 새로 추가한 섹션 종결어미가 문서 전체와 같은지(워크스루 반말 실수 잦음). 위 캐주얼 표 재훑기. 볼드·`—`·"핵심은".
- **형식(사용자 편집 후 재확인)**: frontmatter 빈 줄 / 코드블록 빈 줄 / 코드펜스 `id="..."` — 에디터가 되돌림.

놓치지 말 것:

- 여러 갈래 요청은 다 처리(폴더 분리 + 리뷰 → 리뷰만 하고 폴더 잊지 않기).
- **매 변경 후, 커밋 전 `npm run build`** — frontmatter 스키마·이미지 경로·없는 이미지 참조가 조용히 깨진다.
- slug 오타는 외부 링크 전에 고침("Rader" → "Radar").
- **개발 중 스택이 바뀌면 0편 `## 스택` 표에 히스토리를 남긴다.** 조용히 고치지 말고, 바뀐 행에 무엇을 왜 바꿨는지 한 줄 덧붙이거나 표 아래에 짧은 변경 이력을 추가한다.

새 글 뼈대: `npm run new -- "글 제목"` (`seriesOrder`는 직접 추가).
