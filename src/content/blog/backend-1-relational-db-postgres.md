관계형 데이터베이스가 무엇인지, SQL로 데이터를 어떻게 다루는지, 애플리케이션이 PostgreSQL 서버에 어떻게 접속하는지 정리합니다.

## 데이터베이스를 왜 써야 할까?

애플리케이션이 다루는 데이터 중에는 프로세스보다 오래 남아야 하는 것이 있습니다. 사용자 계정, 주문 내역, 로그 같은 데이터입니다.

이런 데이터를 애플리케이션 메모리(변수, 배열)에만 두면 몇 가지 문제가 생깁니다.

* **프로세스가 종료되면 사라집니다.** 재배포하거나 재시작하면 메모리에 있던 데이터가 초기화됩니다.
* **여러 인스턴스가 데이터를 공유하기 어렵습니다.** 애플리케이션을 여러 대로 늘리면 각 인스턴스가 각자 메모리에 서로 다른 값을 갖게 됩니다.

그래서 오래 보관하고 여러 곳에서 공유해야 하는 데이터는 애플리케이션 프로세스와 분리된 저장소에 둡니다. 이런 데이터를 저장하고 관리하는 시스템이 데이터베이스입니다.

## 파일에 저장하면 안 될까?

간단한 프로그램이라면 파일을 저장소로 써도 됩니다. 하지만 여러 요청이 동시에 들어오는 서버에서는 직접 해결해야 할 문제가 많아집니다.

* **동시 접근** — 여러 요청이 동시에 같은 데이터를 읽고 수정하면 한쪽 변경이 다른 변경을 덮어쓰거나 예상하지 못한 상태가 저장될 수 있습니다. 이를 막으려면 잠금 같은 동시성 제어를 직접 구현해야 합니다.
* **부분 실패** — 두 개 이상의 데이터를 함께 변경하는 도중 프로세스가 중단되면 일부 변경만 반영된 상태가 남을 수 있습니다. "모두 성공하거나 모두 실패"를 보장하려면 복구 로직이 필요합니다.
* **조건 검색** — 특정 조건의 데이터만 빠르게 찾으려면 검색 구조나 인덱스를 직접 구현해야 합니다.
* **형식 보장** — 필수 값이 빠졌거나 잘못된 데이터가 저장되지 않도록 매번 검사 로직을 작성해야 합니다.

관계형 데이터베이스는 이 문제들을 해결하는 기능을 기본으로 제공합니다. 동시성 제어, 여러 변경을 "모두 성공하거나 모두 실패"로 묶는 **트랜잭션(transaction)**, 인덱스, 제약 조건입니다.

## 관계형 데이터베이스란

관계형 데이터베이스는 데이터를 정해진 구조의 **테이블(table)** 로 표현하는 **관계형 모델**을 따르는 데이터베이스입니다.

### 테이블, 행, 열

테이블은 행(row)과 열(column)로 구성됩니다. 예를 들어 사용자를 저장하는 `users` 테이블은 이런 모습입니다.

| id | email | created_at |
|---|---|---|
| 1 | `a@example.com` | 2026-01-02 09:00 |
| 2 | `b@example.com` | 2026-01-02 10:30 |

* **열(column)** — `id`, `email`, `created_at`처럼 저장할 항목을 나타냅니다. 각 열에는 이름과 타입, 필요한 규칙을 정의할 수 있습니다.
* **행(row)** — 실제 데이터 한 건입니다. 여기서는 사용자 한 명이 하나의 행입니다. 레코드(record)라고도 부릅니다.

### 스키마와 제약 조건

테이블을 만들 때는 어떤 열이 있고, 각 열이 어떤 타입과 규칙을 가지는지 정의합니다. 이 구조 정의를 **스키마(schema)** 라고 합니다.

예를 들어 `email` 열을 문자열 타입으로 정의하고, "반드시 값이 있어야 한다", "중복되면 안 된다" 같은 규칙을 붙일 수 있습니다. 이런 규칙을 강제하는 장치가 **제약 조건(constraint)** 입니다.

* `NOT NULL` — 값이 비어 있으면 안 됩니다.
* `UNIQUE` — 같은 값이 중복되면 안 됩니다. 이메일처럼 겹치면 안 되는 값에 씁니다.
* `PRIMARY KEY` — 각 행을 고유하게 식별하는 **기본 키(primary key)** 입니다. `NULL`일 수 없고 중복될 수 없습니다. 꼭 `id`라는 이름일 필요는 없습니다.
* `CHECK` — 정한 조건을 만족하는 값만 저장합니다.

```sql
CREATE TABLE users (
  id BIGSERIAL PRIMARY KEY,
  email TEXT NOT NULL UNIQUE,
  age INTEGER CHECK (age >= 0),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

이렇게 정의하면 이메일 없이 사용자를 저장할 수 없고, 같은 이메일을 두 번 저장할 수 없으며, 음수 나이를 저장할 수도 없습니다. `created_at`은 값을 넣지 않으면 `DEFAULT now()`로 저장 시각이 채워집니다.

### 키와 관계

보통 다른 테이블의 기본 키(`PRIMARY KEY`)를 참조하는 열을 **외래 키(foreign key)** 라고 합니다.

예를 들어 `orders` 테이블의 `user_id`가 `users` 테이블의 `id`를 참조한다면 주문이 어떤 사용자의 것인지 표현할 수 있습니다.

```text
users
  id
  1
  2
   ▲
   │ user_id (FK)
   │
orders
  id | user_id | product
  1  |    1    | keyboard
  2  |    1    | monitor
  3  |    2    | mouse
```

열을 외래 키로 지정하면, DB가 존재하지 않는 사용자를 참조하는 주문을 거부합니다.

> 💡 **여기까지 정리하면**
>
> * 데이터는 테이블의 행과 열로 표현합니다.
> * 스키마는 테이블의 구조와 데이터 규칙을 정의합니다.
> * 제약 조건으로 잘못된 데이터가 저장되는 것을 막습니다.
> * 기본 키로 행을 식별하고, 외래 키로 테이블 사이의 관계를 표현할 수 있습니다.

## SQL이란

테이블을 만들고, 데이터를 읽고 쓰는 언어가 **SQL(Structured Query Language)** 입니다.

SQL은 데이터를 어떻게 찾을지보다 무엇을 원하는지 표현하는 선언형 언어입니다. 실제로 어떤 순서로 찾을지는 데이터베이스가 실행 계획을 세워 정합니다.

```sql
-- 행 추가
INSERT INTO users (email)
VALUES ('c@example.com');
-- 조건에 맞는 행 조회
SELECT id, email, created_at
FROM users
WHERE created_at >= '2026-01-01'
ORDER BY created_at DESC
LIMIT 10;
-- 수정
UPDATE users
SET email = 'new@example.com'
WHERE id = 1;
-- 삭제
DELETE FROM users
WHERE id = 2;
```

사용자 입력값을 SQL 문자열에 직접 이어 붙이면, 입력값에 섞인 SQL 조각이 그대로 실행되는 **SQL 인젝션**이 생길 수 있습니다. 그래서 값은 SQL과 분리해서 전달합니다.

```sql
SELECT *
FROM users
WHERE email = $1;
```

`$1` 같은 자리표시자에 실제 값을 따로 전달하는 방식을 **파라미터 바인딩(parameter binding)** 이라고 합니다. 자리표시자 문법은 DB마다 다릅니다(PostgreSQL `$1`, MySQL `?`).

## PostgreSQL이란

관계형 데이터베이스는 데이터를 표현하고 관리하는 모델이고, 이를 구현한 데이터베이스 시스템은 여러 가지가 있습니다.

**PostgreSQL**은 그중 하나인 오픈소스 관계형 데이터베이스 시스템입니다. 같은 관계형 데이터베이스 시스템으로 MySQL, Oracle 등이 있고, SQLite처럼 애플리케이션 안에 내장해 쓰는 것도 있습니다.

### 클라이언트와 서버

PostgreSQL은 애플리케이션 코드 안에 포함되는 라이브러리가 아니라 별도로 실행되는 데이터베이스 서버입니다.

애플리케이션은 클라이언트가 되어 PostgreSQL 서버에 접속해 SQL을 보내고 결과를 받습니다. 서버는 애플리케이션과 다른 프로세스로 실행되고, 환경에 따라 다른 컨테이너나 다른 호스트에서 실행될 수도 있습니다.

### 연결 문자열

클라이언트가 PostgreSQL 서버에 접속하려면 서버의 위치와 인증 정보가 필요합니다. 이를 한 줄로 표현한 것이 **연결 문자열(connection string)** 입니다.

```text
postgres://user:password@db.example.com:5432/myapp
```

| 조각 | 예시 값 | 뜻 |
|---|---|---|
| 스킴 | `postgres://` | PostgreSQL 연결 문자열임을 나타내는 URL 스킴 (`postgresql://`도 같음) |
| 사용자:비밀번호 | `user:password` | 데이터베이스 접속 계정 |
| 호스트 | `db.example.com` | 데이터베이스 서버 주소 |
| 포트 | `5432` | PostgreSQL 기본 포트 |
| DB 이름 | `myapp` | 서버 안에서 접속할 데이터베이스 |

연결 문자열 하나에 "어느 서버의 어느 데이터베이스에 어떤 사용자로 접속할지"가 모두 담깁니다.

> 💡 **여기까지 정리하면**
>
> * PostgreSQL은 관계형 모델을 구현한 오픈소스 데이터베이스 시스템입니다.
> * 애플리케이션은 클라이언트가 되어 PostgreSQL 서버에 접속합니다.
> * 연결 문자열에는 서버 위치와 인증 정보, 데이터베이스 이름이 들어 있습니다.

## 언제 관계형 DB를 쓸까?

관계형 데이터베이스는 다음과 같은 경우에 잘 맞습니다.

* **구조가 일정한 데이터** — 사용자, 주문, 로그처럼 비슷한 구조의 데이터를 반복해서 저장하는 경우
* **정확성과 일관성이 중요한 데이터** — 결제, 재고, 주문처럼 데이터가 잘못되면 문제가 되는 경우
* **조건을 걸어 조회하는 데이터** — 특정 사용자, 특정 기간, 특정 상태를 기준으로 데이터를 조회하는 경우
* **서로 연결된 데이터** — 사용자와 주문처럼 테이블끼리 참조하는 경우

반대로 다른 저장소가 더 맞는 경우도 있습니다.

* **짧은 시간 동안 자주 변경되는 데이터** — 요청 수 카운터나 쿨다운처럼 금방 필요 없어지는 데이터는 Redis 같은 인메모리 저장소가 낫습니다.
* **구조가 제각각인 데이터** — 레코드마다 구조가 크게 다르고 스키마를 유연하게 가져가야 한다면 MongoDB 같은 문서형 데이터베이스를 고려합니다.

다만 PostgreSQL도 `JSONB` 타입을 지원하므로, 구조가 유동적이라는 이유만으로 문서형 데이터베이스를 골라야 하는 것은 아닙니다.

"관계형 DB는 느리고 Redis는 빠르다"로 나누기보다, 데이터를 얼마나 오래 둘지, 구조가 어떤지, 어떻게 읽고 쓰는지를 보고 저장소를 고릅니다.

## 정리

* 애플리케이션 메모리는 프로세스가 종료되면 사라지므로, 오래 보관할 데이터는 별도의 저장소가 필요합니다.
* 관계형 데이터베이스는 테이블과 스키마로 데이터를 구조화하고, 제약 조건과 트랜잭션 같은 기능으로 데이터의 일관성을 관리합니다.
* SQL은 테이블을 만들고 데이터를 읽고 쓰는 언어입니다.
* PostgreSQL은 관계형 모델을 구현한 오픈소스 데이터베이스 시스템이고, 애플리케이션은 연결 문자열로 PostgreSQL 서버에 접속합니다.
* 데이터의 수명·구조·접근 방식을 보고 관계형 DB, Redis, 문서형 DB 중 맞는 저장소를 고릅니다.
